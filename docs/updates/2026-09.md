## U-20260923-32 · 2026-09-23 · Asyncio templates resolve host names without the loop's thread pool · #done #bugfix

- **What** (`progress.md` #13): the coap, nats and opcua templates run an asyncio loop per step (coap) or per user (nats, opcua). Under Locust on Windows, a host name lookup on such a loop never returns. Reproduced: after `gevent.monkey.patch_all()`, `asyncio.open_connection("localhost", port)` hangs even inside `wait_for`, while `127.0.0.1` connects. The lookup runs in the loop's thread pool, gevent turns those threads into greenlets, and they never run while the Proactor loop waits on IOCP. U-20260923-31 worked around it for HTTP/3 only.
- **Fix** (`wrapper/user_template/_common.py`):
  - `new_template_event_loop()` returns a loop whose `getaddrinfo` resolves in the calling thread. Under gevent that call is cooperative; without gevent it is a plain blocking call.
  - `run_template_coroutine(coro)` runs a coroutine on such a loop, like `asyncio.run`. The loop is the current loop while it runs, leftover tasks are cancelled, and the loop is closed.
  - coap uses `run_template_coroutine`; nats and opcua create their loop with `new_template_event_loop()`.
  - HTTP/3 uses `run_template_coroutine` too, so its copy of aioquic's `connect` (`_resolve`, `_quic_connect`) is gone and it calls `aioquic.asyncio.client.connect` again.
- **Tests**:
  - `test/test_template_event_loop.py` (4). The main case gives the template loop a thread pool that refuses work and connects to `localhost`; that passes. A contrast case shows that a plain loop does use the pool. The other two check that `run_template_coroutine` returns the result, cancels leftover tasks and raises the coroutine's error.
  - The HTTP/3 real-server tests pass through aioquic's `connect` on the new loop, in the gevent-patched test process.
- **Docs**: `architecture.md` §5, step 3 of adding a template, says to use these helpers instead of `asyncio.run` / `asyncio.new_event_loop()`.
- **Result**: suite 1137 passed, 2 skipped. `ruff check` clean.
