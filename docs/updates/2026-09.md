## U-20260923-02 · 2026-09-23 · MCP server answers again: JSON-RPC over stdio without the SDK · #done #mcp #bugfix

- **Bug**: `loaddensity-mcp` / `python -m je_load_density.mcp_server` never answered `initialize`. Importing the package imports locust, and `locust/__init__.py` calls gevent `monkey.patch_all()`; the `mcp` SDK's stdio transport reads stdin on an anyio worker thread, which after patching is a greenlet that never gets scheduled while asyncio blocks the main thread. Reproduced with a ten-line SDK server: it answers without `import locust` and stays silent with it (mcp 1.30.0, locust 2.46.6, Python 3.12, Windows). With mcp 2.x (since 2026-07-28) it failed earlier still: `Server.list_tools` no longer exists.
- **Fix**: `LoadDensityMCPServer` in `mcp_server/server.py` speaks the protocol itself, like FileAutomation's `server/mcp_server.py`: newline-delimited JSON-RPC 2.0 with `initialize` (echoes 2025-06-18, 2025-03-26 or 2024-11-05, otherwise offers the newest), `ping`, `tools/list`, `tools/call`; notifications get no reply; a tool that raises becomes an `isError` result; unknown tools and methods are JSON-RPC errors. `run_stdio()` keeps a duplicate of the original stdout for the protocol and points fd 1 and `sys.stdout` at stderr, so `print` actions and locust's console output cannot corrupt the stream; both directions are UTF-8. `_TOOLS` and the handlers are unchanged; `build_server()` now returns the new class.
- **Packaging**: the `mcp` extra is empty (kept so `pip install je_load_density[mcp]` still works) and `mcp` left `all`; `uv lock` dropped mcp, starlette, sse-starlette, uvicorn, python-multipart, pydantic-settings and their dependencies. `test/test_dependency_floors.py` now also fails if an extra pulls the SDK back in.
- **Docs**: README (en, zh-TW, zh-CN), the Sphinx installation, MCP and architecture pages (en, zh) and `architecture.md` §3: no `[mcp]` extra needed, 13 tools rather than 11 (`generate_from_openapi` and `generate_from_curls` were missing).
